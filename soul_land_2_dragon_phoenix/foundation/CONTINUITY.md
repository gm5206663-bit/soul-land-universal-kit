# Continuity — event history without a competing live-state panel

CURRENT_STATE.json owns the present checkpoint. TIMELINE.json owns event order
and anchor constraints. continuity_events.json records actual written changes.
These owners are complementary, not three independent versions of current rank.

## Before prose

Read the current state, chapter source coverage and all unresolved consequences
that the next scene can touch. Set the chapter’s start/end event before writing.
If a duration is unspecified, do not fill it by guessing a day or year. A relative
event anchor is sufficient when no absolute calendar has been verified.

## After a written scene

Record the event, source chapter/scene, elapsed time, place, participants,
knowledge gained, relationship changes, consumed resources, item transfers,
injuries/recovery, learning, adaptive integration and downstream consequences.
Update live state once, then regenerate its views. A new chapter cannot start
before its predecessor ends except an explicitly signposted flashback.

## Current ledger

No scenes have been written, so the event list is empty. This is an accurate
zero, unlike the undetermined cultivation rank. Planning events in the timeline
and relationship designs are not retroactively counted as published scenes.

## What must persist

A disclosed secret remains disclosed to its witnesses. A damaged tool stays
damaged. A genuinely learned lesson changes later behavior. A stronger body or
more efficient technique changes old task costs. A person cannot be in two
places at the same time merely because two chapters need them.

Superseded facts need a dated reason and successor. Corrections to fictional
history are not invented as in-world amnesia, and canonical outcomes are not
restored by quietly forgetting new causes.
